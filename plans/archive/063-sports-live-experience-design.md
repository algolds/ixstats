> own. Do not "execute" this file — execute the numbered plans it spawns.

## Vision

Turn MyLeague/MyClub from "open a page and click Simulate" into a living sports
network: persistent live scores (Apple-Sports Dynamic Island), an auto-updating
public feed (ESPN bulletins), a personalized "my scores" surface driven by teams
and leagues the user **follows** (LiveScore), and per-sport play-by-play
commentary that can optionally be enriched by an LLM. The deterministic,
seed-based simulator stays the single source of truth for outcomes; everything
here is **presentation and distribution** layered on top of it.

## Architectural ground truth (from recon — inherit these, don't re-derive)

- **Simulation is deterministic.** `resolveMatch(...)` / `resolveRace(...)` in
  `src/lib/sports/resolver.ts` use a seeded RNG (`createRNG`). Outcomes must
  remain reproducible — **no live feature may change a result.** Live surfaces
  *animate* and *narrate* an already-computed result.
- **Match simulation entry points** are `simulateMatchDay`
  (`src/server/api/routers/sports/seasons/matches.ts:204`) and
  `simulateFullSeason` (`.../seasons/fullseason.ts:204`). Both return resolved
  results. These are the natural fire points for auto-post + live events.
- **A feed bot already exists.** `transition.ts:232` posts to the
  `thinkpagesAccount` with `username: "SportsNews"` via
  `thinkpagesPost.create({ data: { accountId, content, isAutoGenerated: true, ixTimeTimestamp: IxTime.timestampToDate(IxTime.getCurrentIxTime()) } })`.
  Reuse this account + shape for all auto-posts.
- **A live ticker UI already exists.** `src/components/myleague/MatchTickerSim.tsx`
  renders client-side play-by-play. The Dynamic Island reuses its event stream
  rather than inventing a second one.
- **Sports presets** (`src/lib/sports/presets.ts`) already encode per-sport
  metadata (emoji, format, rosters). Per-sport commentary vocabularies extend
  this, not a new registry.
- **Single-page router pattern** is the house convention for instant-nav surfaces
  (see `CLAUDE.md` → MyCountry/Vault routers). A personalized "Scores" hub should
  follow it.

## Increments (build order)

### Increment B → Plan 064 (executable now): Auto-post match results to the feed
The cheapest "feels alive" win and the only one with existing precedent. On
match-day / season simulation, post a results bulletin to `SportsNews`
(scores, notable upsets, champions). See `plans/064-sports-feed-autopost.md`.

### Increment D → Plan 065 (spike now): LLM commentary inference evaluation
Research whether a free LLM (Nemotron 3 Ultra free + alternatives) can generate
per-sport play-by-play as **async enrichment** of resolved events, behind a flag
with a templated fallback. Decision doc + thin prototype.
See `plans/065-sports-llm-commentary-spike.md`.

### Increment A → Plan 066 (to author after 064): Dynamic Island for live games
A fixed, app-shell-level floating "pill" (portal) bound to an in-progress
simulation, expandable like iOS Live Activities.
- **State**: a small global store (`useLiveGameStore` — Zustand or React context
  at the app shell) holding `{ activeGame: { leagueId, seasonId, matchId, home, away, score, clock, events[] } | null }`. `MatchTickerSim` pushes its current event/score into this store; the island subscribes.
- **UI**: collapsed = score + clock + sport emoji; tap to expand = last few events
  + a "Sim next" affordance reusing the consolidated next-match-day logic from
  Plan 059. Mount once in the sports layout (`src/app/myleague/layout.tsx` /
  `src/app/myclub/layout.tsx`).
- **Scope guard**: read-only mirror of the ticker; it must not trigger or alter
  simulation, only display + deep-link.
- **Effort**: M–L. **Risk**: MED (global overlay z-index/portal + mobile layout).

### Increment C1 → Plan 067 (to author after 064): Follow model + personalized "Scores" hub
- **Data model** (`prisma/schema/sports.prisma`): a `SportFollow` join model
  `{ id, userId, targetType: "team" | "league", targetId, createdAt, @@unique([userId, targetType, targetId]) }`.
- **API**: `sports.follow` / `sports.unfollow` / `sports.getMyFollows` /
  `sports.getMyScores` (recent + upcoming results for followed teams/leagues).
- **UI**: a `/myscores` (or a MyLeague router section) personalized board —
  followed teams' latest results, next fixtures, standings deltas — styled like
  LiveScore. Follow buttons on team/league pages.
- **Effort**: L. **Risk**: MED (new model + migration via `db:push:force`).

### Increment C2 → Plan 068 (to author after 065 decision): Per-sport commentary vocabularies
- Extend the resolver's event emission (or a post-resolution narrator) so each
  sport has its own event lexicon (soccer: "GOAL!/yellow card/penalty"; F1:
  "overtake/pit stop/fastest lap"; boxing: "knockdown/round won/TKO"; etc.).
- Wire the LLM enrichment from Plan 065 here behind its flag, templated fallback
  always present.
- **Effort**: M–L. **Risk**: LOW–MED (additive to event stream).

## Sequencing & dependencies

```
059–062 (bug fixes)         ── foundation; land first
        │
        ├─► 064 (auto-post)         ── ships alone, precedent exists
        ├─► 065 (LLM spike)         ── research, parallel to 064
        │
        ├─► 066 (Dynamic Island)    ── after 064; reuses ticker + 059's next-day logic
        ├─► 067 (Follow + Scores)   ── after 064; new model, independent of 066
        └─► 068 (per-sport commentary) ── after 065 decision; feeds 066/064 narration
```

- **064 first** among features — lowest risk, immediate payoff, no new model.
- **065 parallel** — pure research; its outcome shapes 068 (and optionally 064's
  copy + 066's narration).
- **066 and 067 are independent** of each other; either can follow 064.
- **068 last** — depends on the LLM decision and benefits from 066's live surface.

## Open product decisions (resolve when authoring 066–068)

- Dynamic Island: auto-show for *any* in-progress sim, or only for followed
  teams? (Recommend: followed teams once 067 exists; until then, the league the
  user is actively simulating.)
- Auto-post volume: every match day, or only notable events (upsets, champions,
  records)? (Recommend: notable-only by default to avoid feed spam — see 064.)
- Commentary depth without the LLM: how rich should the templated fallback be?

## Why this is a design doc and not five plans now

Authoring 066–068 in detail before 064/065 land would bake in assumptions
(event-stream shape, the live store API, the LLM decision) that those increments
will settle. Per the advisor workflow, direction items become design/spike plans;
the concrete executors (066–068) are authored by a later `/improve` pass once
their predecessors are merged and the open decisions above are made.
