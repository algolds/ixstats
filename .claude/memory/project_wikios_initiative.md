WikiOS replaces MediaWiki's frontend with modern reading/editing experience. MediaWiki stays running headlessly for Parsoid, Lua/Scribunto, and content storage (MySQL).

**Why:** User considers MediaWiki slow, bloated, and outdated but values its extension ecosystem, wikitext standard, and content library.

**How to apply:** WikiOS is a `(wiki-os)` route group inside IxStats, NOT a separate app (memory constraints: 7.2GB server). The visual editor is **contentEditable** (`WikiVisualEditor.tsx`, Parsoid `data-mw` roundtrip), NOT PlateJS — PlateJS is a dep used by other editors but `WikiPlateEditor.tsx` does not exist. Source editor = CodeMirror 6 (`WikiSourceEditor.tsx`). Parsoid REST for wikitext↔HTML, `wiki-bridge.ts` for direct MySQL. Existing PRD at `/ixwiki/WikiOS/NEW-WIKI-PRD.md`, brand identity at `/ixwiki/WikiOS/Brand Identity Tree.md`.

**MediaWiki coupling & independence path (June 21 2026, v2):** WikiOS is a thick client over MediaWiki. Reads = already direct-MySQL via `wiki-bridge.ts` (2057 lines, **100% read-only/SELECT by design**). Writes = MediaWiki Action API (CSRF+session via `csrf-cache.ts`). Rendering = MediaWiki parser + Parsoid — the hard dependency that makes full independence a multi-year parser-rewrite (rejected as YAGNI). Staged plan + coupling matrix in `plans/WIKIOS.md` → "MediaWiki Independence Path" and `src/app/(wiki-os)/README.md`. **Stage 1 (direct-MySQL writes) was deliberately NOT built** — replicating `WikiPage::doUserEditContent` (pagelinks/categorylinks/templatelinks/recentchanges/searchindex/parser-cache) against live prod data is high-risk for ~zero gain while rendering stays coupled. **Stage 2 DONE & live:** Postgres `WikiArticle` shadow store (`wiki_articles` table on prod DB localhost:5433/ixstats) + read-through `lib/wiki-os/article-store.ts` (organic backfill, serves last-known copy when MediaWiki down, deploy-safe passthrough if table missing); wired into `wikios.getWikitext`, invalidated on save. **Stage 2b DONE & live:** `WikiRevision` model (`wiki_revisions` table pushed) — append-only local history; dual-write on save (`saveToMediaWiki`→`recordArticleRevision`, best-effort, falls back to invalidate); read-through history/diff in `page-content.ts` (`getHistory` no-offset / `getDiff` / `getRevisionContent`, MySQL fallback); recentchanges sync cron captures direct-MediaWiki edits (`src/server/cron/sync-wiki-recentchanges.ts`, server.mjs job #12, DB key `cronSchedule_wikiRecentChanges` default */10).
