Achievement scaling for population/GDP/GDP-per-capita is **dynamic, percentile-based** (June 2026, v2). Reworked because absolute thresholds were miscalibrated vs the 144 real countries (median pop 17.7M, median GDP $534B, max GDP/capita only $75.5k → old 100k tier was unattainable, 1M GDP tier auto-granted to all).

**Key architecture gotcha:** there were **two** hardcoded threshold sources. `evaluateCondition` in `src/lib/achievement-service.ts` uses the DB `Achievement.conditionJson` (the AUTHORITATIVE path) and only falls back to the definitions' in-code `condition` fn if conditionJson is null. The conditionJson is generated by `determineCondition()` in `src/lib/achievement-sync.ts` — which had its OWN duplicate copy of every threshold. Editing only `achievement-definitions.ts` does NOT change unlock behavior.

**New model (single source of truth):** `src/lib/achievement-scaling.ts`
- `RARITY_PERCENTILE` (Common→25, Uncommon→50, Rare→75, Epic→90, Legendary→98) + `SCALE_METRIC_BY_ID` (id→metric) = the only config.
- `getScaleThresholds(db)`: cached 10-min snapshot of country percentile values per metric.
- conditionJson rules now carry `{ metric, operator, percentile }`; `evaluateRule` resolves the threshold from `ExtendedAchievementData.scaleThresholds` (populated per check in `checkAndUnlock`).
- Definitions' fallback `condition` fns use `meetsScale(data, metric, RARITY_PERCENTILE.X)`. Descriptions are rank-based ("top N% by …").

**To apply changes:** new conditionJson reaches the DB via `syncAchievements` (auto-runs on next achievements-page load when definition count ≠ DB count; or admin sync / `syncMyCollectorAchievements`).

Separately, a client-side `AchievementNotificationService` (`src/services/DiplomaticNotificationService.ts`) with hardcoded GDP notifications (`LiveDataIntegration.tsx`) is notification-only and never writes `UserAchievement` rows — see [[project_achievements_dual_system]].
